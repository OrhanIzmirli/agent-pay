# Agent Pay - backend (parametric weather insurance)

A parametric rainfall insurance prototype on **Solana devnet**. A fixed
formula decides every payout. Two independent rainfall sources are read for
each policy; when they disagree, the worst-case amount is paid **immediately
on-chain** and only the disputed delta is escrowed while an AI watchdog
explains what it sees. The AI can explain and escalate. It can never pay.

## Run it

```
pip install -r requirements.txt
uvicorn app.main:app --reload --port 8000
```

Swagger docs: http://localhost:8000/docs

Copy `.env.example` to `.env`; it lists every variable the backend reads, what
it does and whether it is optional. Keys never go in code or git.

### Explanation provider (Groq > Claude > rule-based)

The watchdog's explanation text is generated by the first available provider:

1. **Groq** if `GROQ_API_KEY` is set (free tier, default model
   `openai/gpt-oss-120b`, override with `GROQ_MODEL`);
2. else **Claude** if `ANTHROPIC_API_KEY` is set (`claude-opus-5` by default,
   override with `WATCHDOG_MODEL`);
3. else a **rule-based** investigator with the same report shape.

A provider that fails falls through to the next, so the demo never depends on a
model being reachable. All three get the same context (built from the policy's
catalog entry, so the wording matches the product: rainfall in mm, delay in
minutes, ...). Whatever the provider, a deterministic guardrail escalates any
spread of 0.40 or more and makes sure the text states the real floor (a floor
of 0 is never described as paid). The AI never sets or moves an amount. The
startup banner prints which provider is active.

On first start the app generates two devnet wallets next to `app/`:

| file                  | role                              | env override            |
|-----------------------|-----------------------------------|-------------------------|
| `wallet.json`         | insurer wallet - **pays**         | `AGENT_WALLET_KEYPAIR`  |
| `service_wallet.json` | default payee - **is paid**       | `SERVICE_WALLET_ADDRESS`|

Both files contain private keys and are gitignored - **never commit or share
them**. `policies.json` and `escrow_ledger.json` are runtime demo state and
are gitignored too.

## The formula (app/formula.py)

```
payout_ratio  = clamp((trigger_mm - observed_mm) / (trigger_mm - exit_mm), 0, 1)
payout_amount = sum_insured_sol * payout_ratio
```

With several readings, the wettest one gives the **floor** ratio and the
driest the **ceiling**. Sources "disagree" when ceiling - floor > 0.10.

## Pay the floor, escrow the delta

1. `POST /policy/{id}/evaluate` pulls two Open-Meteo products for the
   policy's lat/lon and window (`best_match` and `ecmwf_ifs025`; both free,
   keyless, same provider). A failing source is dropped, never read as 0 mm.
2. The floor amount is sent on-chain right away, dispute or not. A poisoned
   feed can only ever freeze the disputed slice, not the whole payout.
3. If the sources disagree, `decision.investigate()` (the watchdog) explains
   why and recommends `auto_resolve` or `escalate`. A spread of 0.40 or more
   is always escalated. The delta goes into `escrow_ledger.json`.
4. A human calls `POST /policy/{id}/resolve?release=true|false`. Release is a
   second real devnet transfer; void moves nothing. If the watchdog said
   auto-resolve, calling `/evaluate` again settles the delta from fresh
   readings when they agree (partial release if they land in between).

### On-chain escrow vault (deployed) and the JSON fallback

With `AGENT_PAY_ONCHAIN_ESCROW=1` the disputed delta is not just a note in a
file: it is locked in a **program-controlled PDA** and can only leave through
the vault program's `release_escrow` / `void_escrow`, both of which need the
insurer authority's signature and a still-Held escrow.

- Program `agent_pay_vault`, **devnet**, id
  `CvE7xMfwbpMmCz9Pvt6RsG9tHxNUpbuG5KwyGuFHSxCk`
  ([Explorer](https://explorer.solana.com/address/CvE7xMfwbpMmCz9Pvt6RsG9tHxNUpbuG5KwyGuFHSxCk?cluster=devnet)).
  Source, IDL and `Cargo.lock` (dependency pins needed for Anchor 0.30.1) are in
  the sibling `agent_pay_vault/` directory; it was built and deployed with the
  `backpackapp/build:v0.30.1` Docker image.
- One account type, `EscrowAccount { policy_id, payee, amount, authority,
  status }`, PDA seeds `[b"escrow", sha256(policy_id)]`. `release_escrow`
  takes an amount (a partial release returns the remainder to the authority).
  A resolved escrow keeps its rent reserve (~0.0012 SOL) so the Released/Voided
  record stays on-chain.
- `app/solana_vault.py` exposes the same `open_escrow` / `release_escrow` /
  `void_escrow` as `payment.py`, so `main.py` is unchanged. `/evaluate` returns
  `escrow_pda` and `escrow_explorer_link` next to `escrow`.
- **Toggle**: `AGENT_PAY_ONCHAIN_ESCROW=1` picks the vault; unset/0 keeps the
  JSON ledger (`escrow_ledger.json`). The ledger is also the index in vault
  mode, and the fallback: if the on-chain open fails (RPC down, or the policy
  already used its PDA) the escrow falls back to the ledger instead of failing
  an evaluation whose floor is already paid.
- **Unconfirmed payments are not failures.** If the RPC cannot confirm a
  submitted transaction, the API returns HTTP 202 `pending_confirmation` with the
  signature and explorer link, never a plain failure. Calling `/evaluate` (or
  `/resolve`) again only re-checks that transaction; a second payment is never
  sent while one may have landed.

## Products

`GET /products` is the catalog the Playground is built from. One formula and
one escrow flow, four products, each fixing only its metric, default
trigger/exit and data source:

| `product_type` | metric | default trigger / exit | readings |
|---|---|---|---|
| `crop_drought` | Rainfall, mm | 40 / 10 | two live weather models (+ optional satellite) |
| `crop_excess_rain` | Rainfall, mm | 80 / 140 | same |
| `event_weather_cancel` | Rainfall, mm | 5 / 25 | same weather models (+ optional Ticketmaster status) |
| `travel_delay` | Delay, min | 30 / 180 | **demo**: two simulated delay feeds, no live flight data |

Every evaluation carries a `proof` object (each reading with its unit, the
calculation with the real numbers substituted, and a hash of the inputs).

## Cross-domain source: event status (Ticketmaster)

For `event_weather_cancel`, rain is only one reason an event does not go ahead.
If the policy has an optional `venue_name` (or `ticketmaster_event_id`) and
`TICKETMASTER_API_KEY` is set, the backend also reads the event's
`dates.status.code` from the free Ticketmaster Discovery API and adds it as one
more reading of a different kind (`unit: "status"`): cancelled/postponed implies
ratio 1.0, still going ahead 0.0. It goes through the same floor/ceiling maths
and shows up in `proof` as `ticketmaster_event_status`. It is strictly
optional: no key, no match, a timeout or any error skips it and the evaluation
proceeds on the weather readings alone. `simulate_event_status` forces a status
for demos.

## Satellite crop-health vote (Agromonitoring NDVI)

Optional third source. Set `AGROMONITORING_API_KEY` and pass
`{"include_satellite": true}` to `/evaluate`, or force it on stage with
`{"simulate_satellite_ndvi": 0.20}`. Two-step API: the field polygon
(policy `field_polygon`, default a ~25 ha square around lat/lon) is registered
once and its id cached on the policy; then NDVI history and imagery are
pulled for the window (widened 20 days back, because clear scenes are
sparse). The mean NDVI of the latest usable scene is the reading.

**Design choice**: NDVI stays in its own units and votes in payout-ratio
space with `ndvi_trigger` (default 0.55, healthy) and `ndvi_exit` (0.25,
total loss) on the policy, instead of being converted to fake millimetres.
Same formula, own thresholds; floor/ceiling are taken over ratios
(`formula.floor_ceiling_from_ratios`). The watchdog cross-references the
satellite against the weather models explicitly ("weather says drought but
the field is still green").

Image URLs from Agromonitoring embed the API key, so the browser only sees
`GET /policy/{id}/satellite/image?kind=ndvi|truecolor`, which the backend
proxies. A simulated satellite reading gets a synthetic NDVI raster stamped
SIMULATED so the UI has a visual without a key. The live Agromonitoring
path is written against the published API but was not exercised without a
key.

## Cover presets and excess rain

`cover` is `drought` (trigger > exit, default) or `excess_rain` (exit >
trigger, e.g. 80 -> 140 mm). **Decision**: excess rain reuses the same
formula; swapping the threshold order flips its direction, so no separate
flood formula was added. Only validation differs.

## API

| method | path                          | what                                              |
|--------|-------------------------------|---------------------------------------------------|
| POST   | `/policy`                     | create: region, lat, lon, trigger_mm, exit_mm, sum_insured_sol, payee_pubkey?, window_start?, window_end? |
| GET    | `/policy/{id}`                | policy + last evaluation + escrow                 |
| GET    | `/policy`                     | list                                              |
| POST   | `/policy/{id}/evaluate`       | body optional `{"simulate": [{"mm": 30, "label": "A"}, {"mm": 12, "label": "B"}]}` |
| POST   | `/policy/{id}/resolve?release=true` | human resolves the escrowed delta           |
| GET    | `/escrow`                     | ledger                                            |
| GET    | `/wallet/balance`, `/wallet/history` | insurer wallet (old `/agent/*` paths still work) |

Every response carrying a signature also carries an
`https://explorer.solana.com/tx/<sig>?cluster=devnet` link
(`floor_explorer_url`, `escrow.release_explorer_url`).

Evaluation fields the frontend shows: `payout_ratio_floor`,
`payout_ratio_ceiling`, `dispute_status` (`none` | `investigating` |
`escalated` | `resolved`), `floor_amount_sol`, `escrow_amount_sol`,
`readings[]`, `dispute` (summary, suspected_cause, evidence, recommendation,
ai_used, model).

`sum_insured_sol` is capped at 0.05 SOL (`MAX_SUM_INSURED_SOL`) so a typo
cannot drain the demo wallet.

## Demo script

```
python demo_scenarios.py          # simulated readings, deterministic
python demo_scenarios.py --live   # scenario 1 uses real Open-Meteo pulls
```

Scenario 1: sources agree, one formula payout, `dispute_status=none`, no AI.
Scenario 2: forced 30 mm vs 12 mm, floor paid, delta escrowed, watchdog
explanation printed, escrow released, final balance checked. Explorer links
are printed for every real transaction.

Tests (formula, products and proof, watchdog wording, Ticketmaster, payment confirmation): `pytest -q`.

## How it fits together

- `app/formula.py` - pure payout maths, the only place amounts come from.
- `app/models.py` - Policy, SourceReading, DisputeReport, EvaluationResult, DisputeStatus.
- `app/data_sources.py` - two Open-Meteo rainfall products + `simulate_reading()`.
  The v1 crypto/FX/weather query code is still in the file, unused.
- `app/decision.py` - the watchdog. Investigates, explains, recommends. Never pays.
- `app/products.py` - the product catalog (`GET /products`).
- `app/proof.py` - the `proof` object attached to every evaluation.
- `app/ticketmaster.py` - optional event-status source (Ticketmaster Discovery).
- `app/escrow.py` - JSON escrow ledger (default backend, fallback, and index).
- `app/solana_vault.py` - on-chain PDA escrow (`AGENT_PAY_ONCHAIN_ESCROW=1`), same functions as below.
- `app/payment.py` - real devnet transfers (with confirmation retries and the `pending_confirmation` state), plus `open_escrow` / `release_escrow` / `void_escrow`.
- `app/payment_mock.py` - same surface, no chain. Swap the import in `main.py` if devnet is flaky.
- `app/policy_store.py` - JSON policy store.

## Redeploying on Azure Container Apps

Drop `app/`, `requirements.txt` into the deployed project. Secrets / env:
`AGENT_WALLET_KEYPAIR` (JSON array from a funded `wallet.json`),
`SERVICE_WALLET_ADDRESS`, optionally `GROQ_API_KEY` / `ANTHROPIC_API_KEY`,
`TICKETMASTER_API_KEY`, `AGENT_PAY_ONCHAIN_ESCROW=1`. Outbound HTTPS to
`api.devnet.solana.com`, `api.open-meteo.com`, and whichever of
`api.groq.com`, `api.anthropic.com`, `app.ticketmaster.com` you enabled.
See `.env.example` for the full list.
